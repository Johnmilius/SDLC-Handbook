# Pilot evaluation, 2026-11-13

**This is a smoke test, not the evaluation.** Three cases, one run per condition (n = 1 per cell). It cannot show variance and is not statistically meaningful. The full protocol in [RUN.md](../RUN.md) (8 cases, 3 runs, blind scoring with a hand check) is yours to run.

## Setup

| Item | Value |
|---|---|
| Cases | 01 (new feature), 02 (bug fix in existing code), 04 (agent-written diff) |
| Conditions | **Skill:** a fresh subagent told to read `SKILL.md` and `reference.md` and apply them to the case material. **Plain:** a fresh subagent given the case's one-line request and the same material |
| Runner model | Sonnet 5.5 for all six runs |
| Isolation | The runners worked in a scratch folder outside this repository that held only the skill folder and the three case files. They were told to read nothing else. That is isolation by instruction and by distance, not by a sandbox |
| Scorer | A separate fresh subagent (Fable 5.2) given the case material, the key, the rubric and two outputs per case labeled A and B, with rule IDs stripped. It was not told which was which |
| Hand check | The build lead read all six raw outputs and scored them before reading the scorer's results |

## What the outputs actually showed

**Case 01 (new feature): no difference in what was caught.** Both conditions found the off-by-one bound, the wrapping negative, the 400-instead-of-422 response and the worker that ignores the saved value. The plain run wrote the tests. The skill run wrote a plan with questions. The plain model did not need the skill to derive tests from the spec here.

**Case 02 (bug fix): the skill made the difference it was designed to make.** The plain run chose "count `char`s" on its own, fixed the unreported `preview_snippet` in the same change, and wrote the tests alongside the fix. The skill run stopped to ask what `max` counts, asked whether `preview_snippet` was in scope, and ordered the work as pin, fail, fix.

**Case 04 (agent-written diff): no difference in what was caught.** Both found the near-miss dependency, the test that encodes the bug, and the `unwrap()` on user input. The plain review was shorter and gave a verdict with severities. The skill output gave no verdict, because it is a planner and not a reviewer.

## Honest read

- The skill's measurable gain in this pilot comes from **behavior, not detection**: it asks before deciding, it orders the work, and it says what was not verified. On detecting planted defects, a plain request to the same model did as well on two of three cases.
- **The skill is too long on small changes.** It ran to nearly four times its own Tier 1 length target on case 02. The scorer did not penalize that. The lead did, and a developer reading it every day would.
- **A plan is not tests.** On case 01 the plain run handed back working test code. Whether a plan-then-stop step is worth its time is a question only real use can answer.
- With n = 1, a one-point difference is inside the noise. This pilot shows the skill runs, follows its format, cites only real rule IDs and does not invent references. It does not show that the skill is worth adopting.

## Limits of this pilot

- One run per cell. No variance estimate.
- The blind was weak. The skill's fixed format ("Tier proposed", "Questions for you") identifies it even with rule IDs stripped.
- The shuffle put the skill output under label A in all three cases, by chance.
- The scorer and the runners are models from the same family, and the cases were written by the same process that designed the skill.
- The skill was supplied by telling the runner to read two files, not through the real skill loader, so automatic triggering was not tested.
